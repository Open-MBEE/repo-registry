## Policies

- **[Clear end of support](sops/archive-notice.md)** (`archive-notice`): Before a repository is archived, its README says that support has ended and points to any known active forks. Repositories archived before this policy existed count as compliant as they are.
- **[Reviewed changes](sops/change-review.md)** (`change-review`): High-tier repositories (graduated tools, and the registry) need at least one approving review from a code owner, and passing checks, before a change is merged to the default branch.
- **[Named owners](sops/codeowners.md)** (`codeowners`): Every live repository names the people who look after it, in a CODEOWNERS file. That file is the authoritative list of the repository's operators.
- **[Contribution guide](sops/contributing.md)** (`contributing`): Tools from version 1.0, media in use, and the registry itself publish a contribution guide that keeps demands on contributors small, says what kinds of contribution are welcome, and asks for tests with code.
- **[Know and watch your dependencies](sops/dependency-management.md)** (`dependency-management`): Tools from version 1.0, and the registry, turn on Dependabot alerts and publish a short dependency policy: how new dependencies are chosen and how they are kept up to date. Services the project provides pin their direct dependencies.
- **[Keep the history](sops/history-protection.md)** (`history-protection`): Tools from version 1.0, and the registry, protect the default branch from force pushes and deletion, so that its history stays complete for review and audit.
- **[README and license](sops/project-files.md)** (`project-files`): Every live repository has a README that says what it is, and a license file that says how it may be used.
- **[Trustworthy releases](sops/release-integrity.md)** (`release-integrity`): Graduated tools publish each release with a software bill of materials (SBOM), sign it, publish build provenance, and keep built executables out of the source repository.
- **[Block secrets from being pushed](sops/secret-protection.md)** (`secret-protection`): Tools from version 1.0, and the registry, turn on push protection, so that GitHub blocks a push that contains a password, key or token.
- **[Documented security design](sops/security-design.md)** (`security-design`): High-tier repositories keep a short design document that describes the security controls of what they build, and keep it current.
- **[Vulnerability reporting](sops/security-policy.md)** (`security-policy`): Tools from version 1.0, and the registry, publish a security policy that says how to report a vulnerability and who responds, and turn on GitHub's private vulnerability reporting.
- **[Version numbers that mean something](sops/semantic-versioning.md)** (`semantic-versioning`): Tools from version 1.0 number their releases with semantic versioning, so that the version says whether an update is a fix, a feature or a breaking change. Graduated tools also say which releases get fixes, and for how long.
- **[Code scanning](sops/static-analysis.md)** (`static-analysis`): Tools from version 1.0, and the registry, run code scanning on every change and fix critical findings promptly.
- **[Fix known vulnerabilities on time](sops/vulnerability-remediation.md)** (`vulnerability-remediation`): High-tier repositories fix known vulnerabilities on a deadline: critical ones within 14 days, medium and high ones within 60 days, and release the fixes in step with the people who use them.
- **[Least-privilege automation](sops/workflow-least-privilege.md)** (`workflow-least-privilege`): Tools from version 1.0, and the registry, give their GitHub Actions workflows read-only access by default, and set up workflows following GitHub's hardening guidance.
